# Graph: <Name>

> **Відхилення від схеми `containers/template.md` (навмисне):** цей шаблон документує один **LangGraph-граф** (або підграф) всередині контейнера `AI Worker`, а не окремий сервіс/контейнер. Граф не має власних environment variables чи health check у сервісному розумінні — натомість у нього є стан, вузли, умовні переходи та цикли, тому секції нижче адаптовані під це, а не скопійовані 1:1 з `containers/template.md`. Дивись `ai_worker/graphs/environment.md` як приклад заповненого документа за цією схемою.

## 1. Purpose & Scope

Що цей граф виробляє (1-2 речення). Що саме його викликає (Celery task, інший граф як батьківський виклик тощо) і хто споживає результат. Якщо граф має декілька режимів входу (наприклад, "первинна генерація" vs "правки") — перелічити їх тут коротко.

## 2. Invocation Contract

## 3. Graph Structure

Якщо граф свідомо розбитий на фази/під-графи (наприклад, для перевикористання патерну в іншому графі) — перелічити кожну фазу, її призначення одним реченням, і які вузли до неї належать. Якщо граф плаский — написати це явно ("граф не розбивається на під-графи, всі вузли на одному рівні") замість того, щоб просто пропустити секцію.

## 4. Graph Diagram

Візуальна діаграма — Mermaid у markdown, вбудоване зображення, або обидва (оглядова діаграма фаз + детальна діаграма станів/переходів). Обов'язково показати: точку(и) входу, умовні розгалуження, цикли з умовою виходу, точку(и) виходу.

## 5. State Schema (Internal)

Повний стан графа під час виконання, включно з полями, яких немає в публічному контракті §2 (історія спроб, лічильники ретраїв, проміжні/робочі значення). Псевдокод (TypedDict/Pydantic-подібний) є прийнятним і бажаним форматом.

## 6. Nodes

| Node | Phase | Responsibility | Reads | Writes | LLM call | Location |
|---|---|---|---|---|---|---|

Для кожного вузла явно вказати, чи він **спільний** (`ai_worker/nodes/`, перевикористовується декількома графами) чи **специфічний для цього графа** (`graphs/<name>/nodes/`). Не залишати це неявним — це впливає на те, хто "власник" змін у вузлі.

## 7. Control Flow: Routing & Loop Termination

- Умова(и) вибору маршруту на вході графа.
- Умова(и) циклів: що саме інкрементує лічильник, максимальна кількість ітерацій, звідки береться ліміт (константа/конфіг/вхідний параметр).
- Взаємовиключні умови завершення графа (перелічити всі шляхи до `[*]`/END).
- Якщо є фолбек-механізм на випадок вичерпання ретраїв — описати, які кандидати він розглядає і чому.

## 8. Configuration / Tunable Parameters

| Name | Default | Description |
|---|---|---|

Змінні середовища чи константи, що керують поведінкою графа (ліміти ретраїв, пороги якості тощо). Якщо змінна логічно належить до `ai_worker.md` §3 (коли той буде написаний) — позначити це, а не дублювати означення.

## 9. Failure Modes

| Failure | Detection | Recovery |
|---|---|---|

Помилки LLM-виклику (timeout, rate limit), невалідний структурований вивід вузла, вичерпання ретраїв без валідного кандидата тощо. **Якщо певний очевидний failure mode свідомо НЕ існує через архітектурне рішення (наприклад, вузол спроєктований так, що ніколи не повертає помилку) — вказати це явно окремим рядком з посиланням на рішення, а не просто пропустити його.**

## 10. Dependencies

| Dependency | Used by | Notes |
|---|---|---|

Спільні вузли (`ai_worker/nodes/`), файли `prompts/`, інші графи (якщо викликаються як під-графи), зовнішні API (Gemini тощо). Якщо документ спирається на схему з `contracts/`, якої ще не існує — позначити це явно (не вигадувати).

## 11. Logging & Observability

Що логується на рівні кожного вузла (рівень DEBUG/INFO/WARNING/ERROR, які теги — `trace_id`, `attempt_index`, `guild_id` тощо), у форматі, узгодженому з `architecture.md`'s Mosquitto log format. Які поля виходу графа (§2) додатково слугують метриками (наприклад, "скільки спроб знадобилось").

## 12. Open Items / Future Work
